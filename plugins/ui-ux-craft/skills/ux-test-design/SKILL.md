# UX 测试设计

以"用户流程"为主线、以"状态完整性"为兜底的功能测试设计方法。目标是发现真实使用中会暴露的问题，而非穷举边界。

## 何时使用本技能

- 为一个新功能或流程设计测试用例
- 规划 UI 回归测试的范围
- 结构化记录测试中发现的缺陷
- 制定可复用的测试脚本/检查清单

## 测试设计流程

```
1. 梳理用户流程 → 2. 分解步骤与状态 → 3. 设计用例 → 4. 执行与记录
```

### 1. 梳理用户流程

从"用户想完成什么"出发，而非"页面有哪些元素"：

```
流程：用户下单
  登录 → 浏览商品 → 加入购物车 → 填写地址 → 选择支付 → 提交 → 确认
```

每个流程要覆盖：
- 主路径（happy path）
- 异常路径（失败、中断、返回）
- 替代路径（游客下单、换支付方式）

### 2. 分解步骤与状态

每个步骤展开为可测的状态组合：

| 步骤 | 关键状态 |
|------|---------|
| 加入购物车 | 库存不足、已是最大数量、需选规格 |
| 填写地址 | 必填校验、格式校验、异地运费 |
| 提交 | 网络超时、库存刚变、重复提交 |

### 3. 设计用例

用例模板：

```
用例ID: UC-001
流程: 用户下单
前提: 已登录、购物车有 1 件商品
步骤:
  1. 进入结算页
  2. 地址留空
  3. 点击提交
预期: 提交被阻止、地址字段就近报错、错误可读
优先级: 高
```

用例覆盖维度：

- **主路径**：正常流程一遍跑通
- **状态覆盖**：加载/空/错误/成功
- **边界**：极长输入、极多数据、并发操作
- **环境**：不同视口、弱网、断网恢复

### 4. 执行与记录

逐用例执行，发现偏差即记录缺陷。

## 缺陷报告结构

```
缺陷ID: BUG-001
标题: 地址为空时仍可提交订单
用例: UC-001
环境:
  浏览器: Chrome 120
  操作系统: macOS 14 / iOS 17
  设备: 桌面端 / iPhone 14
  视口: 1440×900 / 390×844
  构建版本: staging @ commit abc1234
  网络: WiFi / 弱网(3G) / 断网
严重程度(Severity): 阻断
优先级(Priority): 高
复现频率: 必现 / 偶发(约 30%)
复现步骤:
  1. 购物车有 1 件商品
  2. 进入结算页
  3. 清空地址
  4. 点击提交
实际结果: 订单被创建，地址为空
期望结果: 提交被阻止，提示填写地址
附件: 截图/录屏/控制台日志
```

### Severity 与 Priority 的区别

这是两个独立维度，缺陷报告里常被混为一谈：

| 维度 | 含义 | 决定者 | 例子 |
|------|------|--------|------|
| **Severity（严重程度）** | 对功能的影响有多大 | 测试/开发 | 资讯页白屏 = Severity 高 |
| **Priority（优先级）** | 多快需要修复 | 产品/项目经理 | 资讯页白屏但用户量极小 = Priority 中 |

常见组合：高 Severity + 高 Priority（核心流程阻断，立即修）；高 Severity + 低 Priority（边缘场景的严重问题，排期靠后）；低 Severity + 高 Priority（文案错别字但涉及品牌名，立刻修）。

### Severity 定义

| 级别 | 含义 | 例子 |
|------|------|------|
| 阻断 | 核心流程无法完成 | 下单永远失败 |
| 严重 | 主要功能受损 | 支付成功但无反馈 |
| 一般 | 次要功能或体验问题 | 错误提示位置不对 |
| 轻微 | 美观/文案问题 | 错别字 |

### Priority 定义

| 级别 | 含义 |
|------|------|
| 紧急 | 阻塞发布或线上事故，立即修 |
| 高 | 本迭代必须修复 |
| 中 | 排入近期迭代 |
| 低 | 有空再修或纳入技术债 |

## 响应式与多端测试

响应式和多端覆盖不应只在「环境」维度一笔带过，需作为独立测试维度展开。

### 响应式断点

- 列出项目的断点清单（如 sm/md/lg/xl），在每个断点边界**两侧各测一次**（例如 md 是 768px，则测 767 和 769）。
- 检查横向溢出（`overflow-x`）：窄屏下表格、卡片、长 URL 是否撑破容器。
- 检查触控靶区尺寸：移动端可点击元素不小于 44×44px。
- 检查文字截断与换行：长文本、无空串、多语言文案在窄屏的表现。

### 多端覆盖矩阵

| 端 | 必测浏览器 | 重点关注 |
|------|----------|---------|
| 桌面 | Chrome、Edge、Safari | 浏览器默认样式差异、Safari 日期/`gap` 兼容 |
| 移动 H5 | iOS Safari、Android Chrome、**微信内置浏览器** | 微信 XWeb/旧版 X5 内核差异、iOS 软键盘遮挡、安全区 |
| 平板 | iPad Safari | 断点切换、横竖屏 |

**微信内置浏览器**是国内 H5 的高频差异源，必须单独验证。新版微信使用 XWeb 内核（基于较新 Chromium），旧版及部分场景仍用 X5（TBS）内核；常见问题包括 CSS 特性缺失、`position: sticky` 失效、video 行为差异。

### 弱网与中断

- 用 Chrome DevTools Network 面板的 throttling 模拟 3G/断网。
- 测试断网恢复后列表是否自动重试、loading 是否复位。
- 提交请求中断网，确认失败兜底和输入保留。

## 测试设计原则

1. **流程优先**：测用户做的事，而非页面的元素
2. **状态完备**：每个交互都要覆盖四种状态
3. **可复现**：步骤要精确到任何人能复现
4. **不穷举**：聚焦真实风险，不为覆盖率堆用例
5. **回归友好**：用例可脚本化，便于自动化

## 测试脚本组织建议

```
tests/
├── flows/              # 按用户流程组织
│   ├── checkout.spec.ts
│   └── signup.spec.ts
├── components/         # 按组件
│   └── cart.spec.ts
└── fixtures/           # 测试数据与状态
```

按流程组织比按页面组织更接近真实使用，也更容易在重构后保持稳定。
